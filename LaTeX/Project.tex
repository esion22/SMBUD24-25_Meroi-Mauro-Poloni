\section{Data Injection}
The dataset we used was already pretty much cleaned, and complete but we needed to shape it. 
For obtaining a .json file from the .csv file we had we had to write a Python program that was able to transform and shape the data the way we wanted. Here is the python code we used:
\vspace{1cm}
\begin{lstlisting}[language=Python]
import pandas as pd
import json

# Load the CSV file
csv_file = "PathTSavedCSVfile"
df = pd.read_csv(csv_file)

# 1. Check for missing data
print("Missing values per column:\n", df.isnull().sum())

# 2. Handle missing data
# We drop the rows with missing values 
df = df.dropna()


# 3. Convert to JSON-compatible structure (as per your earlier schema)
json_data = []
for _, row in df.iterrows():
    document = {
        "longitude": row["longitude"],
        "latitude": row["latitude"],
        "ocean_proximity": row["ocean_proximity"],        
        "housing": {
            "median_age": row["housing_median_age"],
            "rooms": {
                "total": row["total_rooms"],
                "bedrooms": row["total_bedrooms"]
            },
            "median_value": row["median_house_value"]
        },
        "population_and_income": {
            "population": row["population"],
            "households": row["households"],
            "median_income": row["median_income"]
        }
    }
    json_data.append(document)

# 4. Save cleaned JSON
output_file = "California_Housing.json"
with open(output_file, "w") as f:
    json.dump(json_data, f, indent=4)

print(f"Cleaned JSON file saved to {output_file}")
\end{lstlisting}

\subsubsection*{Problem regarding the id:}
We grouped these types of queries into a single category because, although they are not very challenging, they provide crucial information about our dataset. The website we obtained the dataset from explicitly mentioned that data cleaning would be necessary. Additionally, as described in section 1.1, the website did not provide detailed information on the dataset, prompting us to execute several queries to better understand its structure.\\
At first, we assigned the \texttt{\_id} in MongoDB to the \texttt{latitude} and \texttt{longitude} coordinates. However, although Compass imported the database without any issues, the logs showed errors. Upon further investigation, we discovered that the problem was likely due to non-unique coordinate values for certain blocks. Subsequently, we altered the database architecture by utilizing the \texttt{\_id} automatically generated by Mongo. Following this adjustment, the errors ceased. To verify our hypothesis regarding the cause, we executed a query to group entries by latitude and longitude. This query showed that some blocks are so closely located that they are detected to have identical latitude and longitude coordinates.

\begin{lstlisting}[language=MongoDB]

      count: { $sum: 1 }
    }
  },
  {
    $match: {
      count: { $gt: 1 }
    }
  }, 
  { $sort: {count :- 1} }

]);

\end{lstlisting}

\subsubsection*{Housing price capped at 501000\$}
The final straightforward query we conducted aimed to verify our suspicion that house prices are limited to 501000\$. To confirm this, we executed the following query:
\begin{lstlisting}[language=MongoDB]
db.HousePricing.countDocuments({
    "housing.median_value": { $gt: 500001 }
});
\end{lstlisting}
and the return was 0 while for the same query with value equal to 500001 the value was 958. This is important because it means that when doing statistic on this we need to remember to remove the richest houses.

To simplify things we says that to be near the 2 block must have a difference of longitude and latititude which is <= 0.01. So we run this difficult query: 

\begin{lstlisting}[language=MongoDB]
db.HousePricing.aggregate([
    // Step 1: Filter for San Francisco area
    {
        $match: {
            longitude: { $gte: -123, $lte: -122 },
            latitude: { $gte: 37, $lte: 38 }
        }
    },
    // Step 2: Self-join to find nearby blocks
    {
        $lookup: {
            from: "HousePricing",
            as: "neighbors",
            let: { currentId: "$_id", currentLongitude: "$longitude", currentLatitude: "$latitude", currentMedianValue: "$housing.median_value" },
            pipeline: [
                {
                    $match: {
                        $expr: {
                            $and: [
                                { $lte: [{ $abs: { $subtract: ["$longitude", "$$currentLongitude"] } }, 0.01] },
                                { $lte: [{ $abs: { $subtract: ["$latitude", "$$currentLatitude"] } }, 0.01] },
                                { $ne: ["$_id", "$$currentId"] } // Ensure different blocks
                            ]
                        }
                    }
                },
                {
                    $project: {
                        _id: 0,
                        longitude: 1,
                        latitude: 1,
                        neighborMedianValue: "$housing.median_value"
                    }
                }
            ]
        }
    },
    // Step 3: Flatten the results to get pairs of blocks
    {
        $unwind: "$neighbors"
    },
    // Step 4: Compute the absolute difference in median house value
    {
        $addFields: {
            differenceInMedianValue: {
                $abs: { $subtract: ["$housing.median_value", "$neighbors.neighborMedianValue"] }
            }
        }
    },
    // Step 5: Sort by the difference in descending order
    {
        $sort: { differenceInMedianValue: -1 }
    },
    // Step 6: Limit to get just 1 result. 
    {
        $limit: 1
    },
    // Step 7: Project the final output
    {
        $project: {
            _id: 0,
            block1: {
                longitude: "$longitude",
                latitude: "$latitude",
                medianValue: "$housing.median_value"
            },
            block2: {
                longitude: "$neighbors.longitude",
                latitude: "$neighbors.latitude",

\chapter{Neo4j}

\section{Dataset Description}
The original dataset comes from \href{https://github.com/neo4j-partners/neo4j-transport-for-london/tree/main}{this github page} and the \href{https://data.london.gov.uk/dataset/tfl-bus-stop-locations-and-routes}{London Datastore website}. The data was provided in csv, with some cypher scripts to load only a small sample of the data corresponding to the metro lines, we then had to clean the bus network data and write our own scripts for it.
This data represents the London transport network from 2010, it is composed of stations, bus stops and the connections between them. The structure is a graph with:
\begin{itemize}
    \item \textbf{Nodes}: Representing metro/train stations and bus stops.
    \item \textbf{Relationships}: Representing connections between these nodes based on transport lines and bus routes.
\end{itemize}

\subsection*{Nodes}
\subsubsection*{Stations}
\begin{itemize}
    \item Represents metro/train stations.
    \item Key properties:
          \begin{itemize}
              \item \textbf{zone}: Fare zone of the station (a number between 1 and 3).
              \item \textbf{latitude, longitude}: Geographic coordinates.
              \item \textbf{name}: Name of the station.
          \end{itemize}
\end{itemize}

\subsubsection*{Bus Stops}
\begin{itemize}
    \item Represents bus stops in the transport network.
    \item Key properties:
          \begin{itemize}
              \item \textbf{bus\_stop\_code}: Unique identifier for the stop.
              \item \textbf{latitude, longitude}: Geographic coordinates.
              \item \textbf{name}: Name of the bus stop.
              \item \textbf{stop\_area}: Area identifier grouping related stops.
              \item \textbf{stop\_Code\_LBSL}: Unique code assigned to the stop by London Bus Services Limited.
              \item \textbf{naptan\_ATCO\_code}: Association of Transport Coordinating Officers code according to the UK’s National Public Transport Access Nodes system.
              \item \textbf{virtual\_stop}: Indicates if the stop is virtual (1 for virtual, 0 for physical).
          \end{itemize}
\end{itemize}

\subsection*{Relationships}
\subsubsection*{\textbf{CONNECTED\_BY}}
\begin{itemize}
    \item Connects two \textbf{Station} nodes.
    \item Key property:
          \begin{itemize}
              \item \textbf{line}: The transport line (e.g.``TFL RAIL") connecting the stations.
          \end{itemize}
\end{itemize}

\subsubsection*{\textbf{NEXT\_STOP}}
\begin{itemize}
    \item Connects two \texttt{BusStop} nodes.
    \item Key properties:
          \begin{itemize}
              \item \textbf{route}: The bus route number.
              \item \textbf{heading}: Directional information for the route.
              \item \textbf{run}: A number that indicates different variations of the route.
              \item \textbf{virtual}: Specifies if the connection involves a virtual stop.
          \end{itemize}
\end{itemize}

\section*{Key Characteristics}
\begin{itemize}
    \item The dataset is geospatially aware, with \textbf{latitude} and \textbf{longitude} available for each node, enabling geographic computations such as distances and nearest neighbors..
    \item Metro stations and bus stops are \textbf{not directly connected} in the graph, as they represent distinct transport layers.
\end{itemize}
\subsection{Data Injection}
we used this python script to add a next stop column in the ``london\_transport\_datasets\_routes.csv" we uploaded the processed dataset in the ``london\_transport\_datasets\_routes\_processed.csv" file, this is used later to create the NEXT\_STOP relation in neo4j.

\begin{lstlisting}[language = Python]
    import pandas as pd
df = pd.read_csv('london_transport_datasets_routes.csv')

# Sort the values
df = df.sort_values(by=['Route', 'Run', 'Sequence'])

# Add a colon for the next stop
df['Next_Stop_Code_LBSL'] = df.groupby(['Route', 'Run'])['Stop_Code_LBSL'].shift(-1)

df.to_csv('london_transport_datasets_routes_processed.csv', index=False)   
\end{lstlisting}]

The ``london\_transport\_datasets\_routes\_processed.csv" file was still quite big so we decided to split it in multiple csv files. This allowed us to import the dataset in smaller steps, in this specific use case we decided to split it in 6 files composed of 10.000 lines each.

\end{lstlisting}

This command connects the bus stops and labels the connections according to bus lines they represent. Some heading values were null, we decided to replace these values with ``Unknown".\\
The ``london\_transport\_datasets\_routes\_processed.csv" file is quite big, the following query loads the whole csv file, you can replace ``file:///london\_transport\_datasets\_routes\_processed.csv" with ``file:///london\_transport\_datasets\_routes\_processed\_part1.csv" and repeat the query for each file from part1 to part6.

\begin{lstlisting}[language=Cypher]
LOAD CSV WITH HEADERS FROM "file:///london_transport_datasets_routes_processed.csv" AS row
MATCH (start:BusStop {stop_Code_LBSL: row.Stop_Code_LBSL})
MATCH (end:BusStop {stop_Code_LBSL: row.Next_Stop_Code_LBSL})
MERGE (start)-[rel:NEXT_STOP]->(end)
ON CREATE SET
    rel.route = row.Route,
    rel.run = row.Run,
    rel.heading = COALESCE(row.Heading, "Unknown"),
    rel.virtual = row.Virtual_Bus_Stop;
\end{lstlisting}

\section{Queries}
\subsection{Queries for Generating Paths}
Let us start with some queries that allow us to visualise the data like in figure below.\\
\begin{figure}[h]
    \centering
    \includegraphics[width=1\linewidth]{metropolitan-line-2024.png}
    \caption{Metropolitan line}
\end{figure}
\\The first one that comes to mind is a query that allows us to see all the stations in a train line.
We can do this with this simple match that searches all the nodes connected to a line. This is a very simple query but probably one of the most useful ones so we decided to include it anyway:\\
\begin{lstlisting}[language=Cypher]
MATCH (start:Station)-[:CONNECTED_BY {line: "METROPOLITAN"}]-(end:Station)
RETURN DISTINCT start.name
\end{lstlisting}

This is the same query but for the bus network: \\
\begin{lstlisting}[language=Cypher]
MATCH (start:BusStop)-[:NEXT_STOP {route: "154"}]-(end:BusStop)
RETURN DISTINCT start.name AS BusStop
\end{lstlisting}

If we want to visualise the nodes in Neo4j Browser, we can simply replace "DISTINCT start.name" with start.\\

If we can't visualize the graph generated from Neo4j Broweser it can be hard to understand the available paths. The following query is a variation of the previous query that returns all the paths from the terminal stations.\\
This is done by filtering the start and end nodes by the number of connection and by eliminating all the paths where a node appears more than one time. The query returns the path only in one direction (from A to B and not from B to A, where A has a lower id number):

\begin{lstlisting}[language=Cypher]
MATCH path = (start:Station)-[:CONNECTED_BY* {line: "METROPOLITAN"}]->(end:Station)
WHERE size([(start)-[:CONNECTED_BY {line: "METROPOLITAN"}]-() | 1]) = 2
  AND size([(end)-[:CONNECTED_BY {line: "METROPOLITAN"}]-() | 1]) = 2
  AND ALL(n IN nodes(path) WHERE SINGLE(x IN nodes(path) WHERE x = n))
  AND id(start) < id(end)
RETURN 
  [node IN nodes(path) | node.name] AS Route,
  length(path) AS RouteLength
ORDER BY RouteLength DESC
\end{lstlisting}

Another useful feature is the ability to search for the reachable stations or bus stops from a specific position.
The following querys returns all the stations or bus stops reachable in 3 steps. In this specific case it returns all the station names and path length from the ``Stratford" station :

\begin{lstlisting}[language=Cypher]
MATCH path = (start:Station {name: "Stratford"})-[:CONNECTED_BY*..3]-(reachable)
RETURN DISTINCT 
  reachable.name AS ReachableNode,
  length(path) AS PathLength
ORDER BY PathLength ASC
\end{lstlisting}

This is the same query but with the bus stops:

\begin{lstlisting}[language=Cypher]
MATCH path=(start:BusStop {name: "WHITGIFT CENTRE"})-[:NEXT_STOP*..3]-(reachable)
RETURN DISTINCT 
  reachable.name AS ReachableNode,
  length(path) AS PathLength
ORDER BY PathLength ASC
\end{lstlisting}

The following query allows us to see how connected are all the stations, it returns the number of lines that are connected to each station and orders them in descending order. This data can be a bit deceiving because "King's Cross St Pancras" is ranked only fifth in the ranking, this station is the one with the most underground lines and someone might argue that underground lines are better that normal train lines for everyday activities.

\begin{lstlisting}[language=Cypher]
MATCH (s:Station)-[r:CONNECTED_BY]->()
WITH s, count(DISTINCT r.line) AS num_lines
WHERE num_lines > 1
RETURN s.name AS Station, num_lines AS NumberOfLines
ORDER BY num_lines DESC
\end{lstlisting}

All the queries that we just saw analyze the bus and train networks by themselves. It can be useful to see the closest train station to a specific bus stop. We can do it in this way by filtering the nodes using the latitude and longitude:

\begin{lstlisting}[language=Cypher]
MATCH (bus:BusStop {name: "WHITGIFT CENTRE"}), (station:Station)
WITH bus, station,
  point({latitude: bus.latitude, longitude: bus.longitude}) AS busPoint,
  point({latitude: station.latitude, longitude: station.longitude}) AS stationPoint
RETURN bus.name AS BusStop, 
       station.name AS NearestStation,
       point.distance(busPoint, stationPoint) AS Distance
ORDER BY Distance ASC
LIMIT 5
\end{lstlisting}

A variation of this query is this one that finds the 10 bus stops and stations that are closest to each others:

\begin{lstlisting}[language=Cypher]
MATCH (bus:BusStop), (station:Station)
WITH bus, station,
  point({latitude: bus.latitude, longitude: bus.longitude}) AS busPoint,
  point({latitude: station.latitude, longitude: station.longitude}) AS stationPoint
RETURN bus.name AS BusStop, station.name AS NearestStation,
  point.distance(busPoint, stationPoint) AS Distance
ORDER BY Distance ASC
LIMIT 10 
\end{lstlisting}

\subsection{Other queries}

These queries are interesting mainly for statistical purposes and they are here to quantify the informations in the dataset.\\

This query returns the number of stations, bus stops and the average station and stop connections:
\begin{lstlisting}[language=Cypher]
MATCH (bus:BusStop)
WITH count(bus) AS NumberOfBusStops, avg(COUNT { (bus)-[:NEXT_STOP]->() }) AS AvgBusStopConnections

MATCH (station:Station)
WITH NumberOfBusStops, AvgBusStopConnections, count(station) AS NumberOfStations, avg(COUNT { (station)-[:CONNECTED_BY]->() }) AS AvgStationConnections

RETURN NumberOfBusStops, NumberOfStations, AvgBusStopConnections, AvgStationConnections

\end{lstlisting}



This query allows us to see the number of stops for each bus or train line. the results are ordered by the number of stops in descending order:
\begin{lstlisting}[language=Cypher]
MATCH (station1:Station)-[r:CONNECTED_BY]->(station2:Station)
WITH DISTINCT r.line AS Line, collect(DISTINCT station1) AS Stops
RETURN Line AS Route, size(Stops) AS StopCount, "Tain or Metro" AS Type ORDER BY StopCount DESC

UNION

MATCH (busStop1:BusStop)-[r:NEXT_STOP]->(busStop2:BusStop)
WITH DISTINCT r.route AS Route, collect(DISTINCT busStop1) AS Stops
RETURN Route, size(Stops) AS StopCount, "Bus" AS Type ORDER BY StopCount DESC
\end{lstlisting}

This query returns the average distance between each bus stop and station:

\begin{lstlisting}[language=Cypher]
MATCH (bus:BusStop), (station:Station)
WITH bus, station,
  point({latitude: bus.latitude, longitude: bus.longitude}) AS busPoint,
  point({latitude: station.latitude, longitude: station.longitude}) AS stationPoint
WITH point.distance(busPoint, stationPoint) AS Distance
RETURN avg(Distance) AS AverageDistance
\end{lstlisting}

This last query is here to highlight some anomalies in the dataset, in particular there is a surprising amount of bus stops (315 nodes) that are not connected to any other node, also there are 883 virtual stops (stops that do not have a physical structure to indicate them and were also probably temporary), 31 of these virtual stops have a missing name that we replaced with ``Unknown".

\begin{lstlisting}[language=Cypher]
MATCH (bus:BusStop)
WHERE NOT (bus)-[:NEXT_STOP]->()
RETURN count(bus) AS Count, 'UnconnectedBusStops' AS Type

UNION

MATCH (bus:BusStop)
WHERE bus.virtual_stop = "1"
RETURN count(bus) AS Count, 'VirtualBusStops' AS Type

UNION

MATCH (bus:BusStop)
WHERE bus.name = "Unknown"
RETURN count(bus) as Count, 'MissingName' AS Type
\end{lstlisting}

\subsection{Neo4j}
The Neo4j notebook aims at exploring the \textit{London Datastore} Dataset, showing a map of the buses and undergrounds of the English capital.\\
The main focus of the notebook is of developing a path finding algorithm that builds a path that goes from one station (bus or underground) to another.\\
The challenging part of this algorithm was taking into consideration the fact that not all stops are directly connected to one another; indeed, sometimes a path may require you to cover some distance by foot. In order to achieve this, the fields describing the coordinates of the stations have proven to be very useful, since they allowed setting a maximum distance one can cover by foot.\\
It must be said that the algorithm is far from perfect, since it aims at finding \textit{one} path and not the best path. It can sure be improved by taking into consideration the time that it takes to travel from one stop to another using the bus or the underground, or by making it choose the path with the smallest number of changes. Although it is not perfect, it can be a starting point in developing a far more efficient and useful path finding algorithm in the London transportation network.\\\\
